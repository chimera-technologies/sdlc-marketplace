Cross-cutting layers

These run underneath every stage. They are why the loop can move faster without the controls falling behind.

Agent configuration

Owned by platform and tech leads, changed through PRs and regression-tested like code
CLAUDE.mdSkillsHooksREVIEW.mdSubagents gated byEval suite
  • The eval suite holds 20–50 real tasks with accepted outcomes. It runs on any PR touching CLAUDE.md or .claude/** and nightly; a drop in pass rate blocks the config change.
  • Feedback in: a mistake flagged twice in review goes into CLAUDE.md, and every incident or vulnerability class that ships a fix becomes a new eval.
  • Policy changes flow into skills and are signed off by the policy owner. Anything that must always hold is backed by a hook, because skills are advisory.

Platform controls

Deployed by platform or IT through managed settings; engineers cannot override them
  • Permission allow and deny lists, bypass mode disabled, managed rules only.
  • OS-level sandbox with a network domain allowlist and credential reads denied (~/.ssh, cloud keys, tokens).
  • Managed hooks only, a managed MCP allowlist, and an approved plugin marketplace as the only source of skills, agents and hooks.
  • A minimum Claude Code version, and CI runners that hold short-lived scoped tokens with no standing production credentials.

Evidence and measurement

Where the audit trail and the stage metrics come from
  • Git history for every artifact: author, timestamp, approver. The chain of commits is the audit record.
  • OpenTelemetry export for sessions, skill invocations and every hook allow or block decision.
  • PR metadata, CI logs, the incident tracker and scan history feed the leading and lagging indicators shown on each stage, plus DORA measures.

Systems of record

Name one source of truth per artifact
  • Repo first: markdown artifacts are authoritative and Jira or ServiceNow link to the commits.
  • Legacy first: the existing tool holds the record; Claude reads it at session start and writes the outcome back through MCP.
  • Linkage as the minimum: each artifact names its record ID and each record holds the commit SHA. A good starting point, with two sources of truth accepted.

Git mechanics

  1. Each artifact is written on its own branch and opened as a PR into the protected branch.
  2. The owner's merge is the sign-off, timestamped in git history.
  3. CI path filters react to the folder touched and start the next job headless.
  4. That job opens its own branch and PR for the next artifact, so the next reviewer is notified.

One repo with an intent/ folder is the simplest setup. Use a dedicated intent repo only when intents span many repositories.

Two limits worth stating on the diagram

  1. A PreToolUse hook gates Claude's own tool calls. A deploy step that CI runs without Claude also needs environment protection rules in the CI platform.
  2. The agent that wrote a change can never approve it. Branch protection and the production gate stay human in every mode.
